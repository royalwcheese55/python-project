# read-thru/ write thru
**read thru cache** is when a read request is made, the cache first checks if the data is available(cache hit).
if data not in cache(cache miss), the cache system reads the data from primary database stores it in cache and then return data to client.
later read request for same data will be served directly from cache until data expires or is evicted.

pro: data consistency and reduces load on primary storage
con: latency on cache miss

**write thru cache** is when a write request is made, data is written to cache and primary storage at the same time. read request can then be served from cache, contains up-to-date data.

pro: data concsistency and no data loss on crash
con: higher load on primary storage and latency on write operations

**key difference** is read thru focus on loading and serving read-heavy data(read requently but updated less often)
write thru focus on maintaining high data integr  ity and consistency between cache and database, essential for transactional data where write is critical.

# BASE
BASE stands for basically available, soft state, and eventually consistent. The acronym highlights that BASE is opposite of ACID, like their chemical equivalents.

Basically available
Basically available is the database’s concurrent accessibility by users at all times. One user doesn’t need to wait for others to finish the transaction before updating the record. For example, during a sudden surge in traffic on an ecommerce platform, the system may prioritize serving product listings and accepting orders. Even if there is a slight delay in updating inventory quantities, users continue to check out items.

Soft state
Soft state refers to the notion that data can have transient or temporary states that may change over time, even without external triggers or inputs. It describes the record’s transitional state when several applications update it simultaneously. The record’s value is eventually finalized only after all transactions complete. For example, if users edit a social media post, the change may not be visible to other users immediately. However, later on, the post updates by itself (reflecting the older change) even though no user triggered it.

Eventually consistent
Eventually consistent means the record will achieve consistency when all the concurrent updates have been completed. At this point, applications querying the record will see the same value. For example, consider a distributed document editing system where multiple users can simultaneously edit a document. If User A and User B both edit the same section of the document simultaneously, their local copies may temporarily differ until the changes are propagated and synchronized. However, over time, the system ensures eventual consistency by propagating and merging the changes made by different users.

# monolithic vs microservices
monolithic application is a single unified software unit where all components(ui, data access, business logic) tightly coupled and built as one large indivisble block, sharing a single codebase and deployment.

single codebase: all features reside in on large repo
unified deployment: entire app is built deployed and scale as one entity
tight coupling: components are interdependent, sharing resources and logic
single process: run as one logical executable.

simple deveplopment and low latency 
large/complex codebase makes it harder to scale and maintenance, slow updates, lack of flexibility.

microservices is a collection of small independent, loosely coupled services, each responsible for a sepcific business function, communicate via api(http), it allowed different services to be scale/develop in different languages without affecting entire system.

independent & autonomous: each service run as its own process
loosely coupled minimize the dependencies between them
resilient: failure in one service typically doesn't bring down entire application

# kafka topics
log of events: topic is continuous, append-only log, meaning new messages are always added to the end, and existing messages are immutable

partitions: topics are split into partitions, which are ordered sequences of messaged that enable parallelism and high throughput by allowing multiple consumers to read data concurrently.

durable: messages are stored durably on disk and replicated across multiple kafka brokers for fault tolerance.

key-value: messages within a topic are typically structured as key-value pairs, with optional metadata like timestamps

decoupling: separate data producers from consumers, allowing them to operate independently and at their own pace.

**kafka producer**: client application that write data, in the form of events or messages(keys, values, timestamps) into kafka topics.
data serialization, convert data into byte arrays before sending it to broker
partitioning, decide which topic partition to write to
load balance, balance data acroos brokers
reliability(acks), producers can be configured to wait for acknowledgements from brokers to ensure data delivery
acks configures how many broker replicas must recieve a record before a producer considers a request successful, tranding off speed for durability

acks = 0 fire and forget, no acknowledgment needed, fastest, risk of data loss
acks = 1 leader acknowledgement only(default)
acks = all all in-sync replicas must acknowledge, slowest, high durability

**kafka consumer**: client applications that subscribes to topics and processes incoming data streams from kafka brokers. operating via a pull model, consumers fetch messages and track position using offsets.
read records from topics and process them, storing the results indb or trigger actions
consumer groups, multiple consumers can share a group.id to divide topic partitions among themselves, enabling horizontal scalability
pull model, instead of brokers pushing data consumers request data when they are ready to prevent overload.

# saga pattern (relational database)
manage data consistency acroos microservices in distributed system by replacing long-lived, monolithic transactions with a sequence of atomic transactions.
each service update its own database and triggers next step via events, if step fails saga undo preceding changes.

choreography based: service exchange events without a central controller, each service listen and trigger events.
Orchestration based: central controller tells participants which local transactions to execute.
